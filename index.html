DBMS Documentation

Academic design for AirWatch.

1. Project Abstract

AirWatch is an air-quality monitoring and historical analysis system designed to organize sensor stations, air-quality readings, and pollution alerts in a relational database.

2. ER Relationships

USERS
PK user_id
name, email
password_hash, role
SENSORS
PK sensor_id
sensor_name, location
latitude, longitude, status
READINGS
PK reading_id
FK sensor_id
recorded_at, pm25, pm10
co2, aqi
ALERTS
PK alert_id
FK sensor_id
FK reading_id
alert_type, severity, status

Relationships: One sensor has many readings. One sensor can have many alerts. A reading can generate zero or more alerts. Users are stored separately for authentication and authorization.

3. Functional Dependencies

  • Users: user_id → name, email, password_hash, role, created_at. Also, email → user_id, name, password_hash, role, created_at because email is unique.
  • Sensors: sensor_id → sensor_name, location, latitude, longitude, status, created_at.
  • Readings: reading_id → sensor_id, recorded_at, pm25, pm10, co2, aqi.
  • Alerts: alert_id → sensor_id, reading_id, alert_type, message, severity, created_at, status.

4. Normalization

1NF: Each field stores a single value, and each row has a unique primary key.

2NF: Each table uses a single-column primary key, so there are no partial dependencies on part of a composite primary key.

3NF: Non-key attributes depend on the key, the whole key, and nothing but the key. Sensor details are stored in sensors rather than repeated in every reading. User details are stored separately.

5. SQL CRUD Examples

-- CREATE
INSERT INTO sensors
(sensor_name, location, latitude, longitude, status)
VALUES ('Sensor A', 'Campus', 16.30, 80.45, 'Active');

-- READ
SELECT * FROM sensors;

-- UPDATE
UPDATE sensors SET status = 'Inactive'
WHERE sensor_id = 1;

-- DELETE
DELETE FROM sensors WHERE sensor_id = 1;

-- AGGREGATE REPORT
SELECT sensor_id, AVG(aqi) AS average_aqi,
MAX(aqi) AS highest_aqi
FROM readings GROUP BY sensor_id;

6. Views and Transactions (MySQL)

CREATE VIEW daily_air_quality_summary AS
SELECT DATE(recorded_at) AS reading_date,
COUNT(*) AS total_readings,
AVG(aqi) AS average_aqi,
MAX(aqi) AS highest_aqi
FROM readings
GROUP BY DATE(recorded_at);

CREATE VIEW sensor_reading_summary AS
SELECT s.sensor_id, s.sensor_name, s.location,
COUNT(r.reading_id) AS total_readings,
AVG(r.aqi) AS average_aqi,
MAX(r.aqi) AS highest_aqi
FROM sensors s
LEFT JOIN readings r ON s.sensor_id = r.sensor_id
GROUP BY s.sensor_id, s.sensor_name, s.location;

-- Transaction demonstration (run in MySQL)
START TRANSACTION;
INSERT INTO readings
(sensor_id, recorded_at, pm25, pm10, co2, aqi)
VALUES (1, NOW(), 40, 70, 450, 160);

SET @new_reading_id = LAST_INSERT_ID();

INSERT INTO alerts
(sensor_id, reading_id, alert_type, message, severity, status)
VALUES (1, @new_reading_id, 'HIGH_AQI',
'AQI threshold exceeded', 'High', 'Open');

COMMIT;

-- For a test that should be undone:
START TRANSACTION;
INSERT INTO readings
(sensor_id, recorded_at, pm25, pm10, co2, aqi)
VALUES (1, NOW(), 10, 20, 400, 40);
ROLLBACK;

Run these SQL examples in your actual MySQL database after creating the required tables. The website's demonstration data is not connected to MySQL.

7. Testing Checklist

  • ☐ Add, search, edit, and delete a sensor.
  • ☐ Add, filter, edit, and delete a reading.
  • ☐ Verify chart and report updates.
  • ☐ Resolve an alert and check the open-alert count.
  • ☐ Test MySQL views and transaction rollback in a database client.
  • ☐ After backend integration, test login, authorization, and persistence after refresh.
